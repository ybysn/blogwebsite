# 网站工程工作流

本文件从 AI Engineering Protocol 提取适用于本博客网站（Next.js 16 + MDX 静态博客）的准则。

---

## 每次任务流程

**Before coding：**
1. 先阅读相关文件 — `CLAUDE.md`（项目概览）、目标组件/页面代码、引用的 lib 模块。不要猜测。
2. 总结需求理解、影响范围、现有实现。
3. 明确假设；如果无法合理假设，先提问。

**计划门槛：**
- 新页面 / 新组件类型 / 架构变动 → 必须先说明范围、影响文件、验证计划，再写代码。
- 单文件编辑 / 纯内容修改 → 说明改什么然后执行。
- 跨文件改动 / 陌生模块 / 高风险任务 → 给出分阶段计划和验证方式。

**While coding：**
- 按最小影响范围修改代码。优先沿用现有模式（server→client 分离、Tailwind 样式、i18n 命名）。
- 不修改与当前任务无关的文件，不做无关重构。
- 每个关键阶段后说明进展。

**After coding：**
- 运行 `npm run build` 验证。构建通过是最低交付标准。
- UI 和交互改动尽量做可视化验证（本地 `npm run dev` 预览）；无法自动验证时，在最终回复中说明未覆盖的视觉风险。
- 交付时给出验证证据：命令 + 退出结果 + 关键输出。

---

## 验证与审查门禁

- **开始实现前先定义通过/失败标准。** 例如：构建通过、测试通过、lint 无错误、特定页面正常渲染。
- **`npm run build` 是强制门禁** — 每次代码修改后必须运行，除非明确说明原因。
- **UI 改动** — 如果在当前环境无法截图或预览，最终回复要明确标注"未验证的视觉风险"。
- **复杂改动后** — 应考虑用新的上下文做二次审查：检查 diff 是否按计划实现、是否覆盖边界、是否有回归风险。

---

## 高风险变更 — 必须先给方案

遇到以下情况必须先写方案，不能直接改：

| 类别 | 示例 |
|------|------|
| **架构调整** | 改 `output: 'export'`、加 API 路由、改页面路由结构 |
| **样式体系** | 改 CSS 变量主题色板、改 Tailwind 配置、替换 Typography 插件 |
| **依赖变更** | 加新 npm 包、升级 Next.js / React 版本 |
| **部署配置** | 改构建命令、改输出目录、改 Nginx 配置 |
| **内容迁移** | 批量重命名 slug、批量修改 frontmatter 结构 |
| **核心组件** | 替换 MDX 渲染链路、改 Giscus / 搜索方案 |

方案至少包含：
- 为什么需要改
- 影响哪些文件/模块
- 兼容性和回滚方式
- 验证方式
- 风险点

## 内容编辑规则

### 写文章

在 `content/posts/` 下创建 `.mdx` 文件，必须包含：

```yaml
---
title: "标题"                  # 必填
date: "2026-06-01"             # 必填，ISO 格式
description: "描述"            # 必填，会出现在 SEO 和列表卡片
tags: ["tag1", "tag2"]         # 必填
published: true                # 必填 — false 表示草稿
category: "network-proxy"      # 必填 — 参考 lib/categories.ts
lang: zh-CN                    # 可选，'en'（默认）或 'zh-CN'
ogImage: "https://..."         # 可选
---
```

### 翻译准则

- 中文自然流畅，不要逐字直译
- 技术术语（DNS、SSH、WAF、CDN 等）保留英文
- 代码块中的注释和字符串保持原文

### 发布控制

- `published: false` — 不在列表展示，但 URL 仍可直达（当草稿用）
- 发布前检查：frontmatter 完整、标签正确、分类在 `lib/categories.ts` 中有定义

## Bug 修复流程

修 bug 时必须遵循：

1. **复现问题** — 不要在未复现的情况下猜测修改
2. **列出至少 2 个可能的根因**
3. **用日志、构建错误、代码路径或数据证明假设**
4. **找到根因后再修改**
5. **修复后运行 `npm run build` 验证**
6. **记录经验**

禁止连续随机试补丁。每次修改前说明：
- 当前假设
- 支持该假设的证据
- 本次修改的预期结果

### 多次失败后的诊断模式

如果连续多次修改仍未解决问题，停止写代码，输出：

- 已尝试的方案
- 每个方案为什么失败
- 已确认的事实
- 未知信息
- 最可能的 3 个根因
- 下一步最小验证实验

## 上下文管理

- 不相关任务不要混在同一个长期会话里
- 上下文被无关探索或长日志污染时，先总结已确认事实、修改文件、验证命令和剩余问题，再开启干净会话继续
- 同一问题被连续纠正超过 2 次时，先沉淀新的事实，再重新开始

---

## 经验沉淀

每次解决问题后，判断经验应该沉淀在哪里：

| 场景 | 沉淀位置 |
|------|----------|
| 可自动化验证 | 测试用例 |
| 可自动化检查 | 检查脚本 |
| 固定流程 | runbook |
| 架构决策 | `docs/adr/` |
| 经验教训 | `docs/lessons-learned.md` |

---

## 最终交付格式

每次完成任务后，回复必须包含：

```md
完成内容：（做了什么）
修改文件：（列表）
验证结果：（构建命令 + 退出码 + 关键输出）
剩余风险：（可能存在的问题）
后续建议：（可选）
```
